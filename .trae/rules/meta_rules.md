# 通用元规则（AI 工作流 · 适用于所有项目）

> **这份规则解决的核心问题**：如何让 AI 助手在跨对话、跨项目中保持一致性，避免每次重复说明，压缩信息熵。

---

## 〇、规则的核心哲学

> **"AI 不是金鱼，每一次对话都该继承上一轮的经验。"**

AI 助手每次新对话都是"失忆"状态。任何**重复试错、重复强调、重复确认**的对话，都是在浪费 API 和时间。本规则的目的就是**把经验沉淀到文件里**，让 AI 通过读取规则文件就能"继承记忆"。

---

## 一、规则体系架构

### 1.1 三层规则分层

```
Trae 全局规则（user_profile.md）        ← 跨项目通用：用户偏好、工作习惯
       ↓
Trae 项目规则（.trae/rules/*.md）       ← 项目特定：架构、约定、踩坑
       ↓
AI 行为规则（本文件）                  ← 元规则：如何更新、如何积累、如何传递
```

### 1.2 项目规则文件位置

- **全局规则**：`c:\Users\King\.trae-cn\memory\user_profile.md`
- **项目规则**：`{项目根目录}\.trae\rules\project_rules.md`
- **本元规则**：`{项目根目录}\.trae\rules\meta_rules.md`（本文件）

### 1.3 规则的加载顺序

新对话开始时，AI 应**优先读取**：
1. `user_profile.md`（全局偏好）
2. 当前项目的 `project_rules.md`（项目约束）
3. `meta_rules.md`（如何更新规则本身）

## 二、自动更新原则

### 2.1 触发更新的时机

**遇到以下情况，必须主动提议更新规则**：

| 触发条件 | 更新位置 | 示例 |
|---------|---------|------|
| 用户纠正了一个 AI 错误 | `project_rules.md` 添加禁忌项 | "PowerShell `Set-Content` 会带 BOM" |
| 发现了一个新的踩坑 | `project_rules.md` 添加经验 | "路径比较前必须 `replace(/^\//, '')`" |
| 用户表达了一个偏好 | `user_profile.md` | "我习惯中文沟通" |
| 完成了一个新功能 | `project_rules.md` 联动表添加 | "新增 KB 文章只改 yml 文件" |
| 每次完整更新完成 | `project_rules.md` 检查清单勾选 | 回答末尾附上检查清单 |

### 2.2 更新的颗粒度

- ✅ **更新**：具体的踩坑、具体的命名规范、具体的文件路径
- ❌ **不要更新**：笼统的"要注意安全"、抽象的"代码要优雅"
- ❌ **不要更新**：只用一次的特殊情况（除非是严重错误）

### 2.3 更新的格式约束

- 每条规则必须**可执行**：能直接转化为代码或操作
- 每条规则必须有**反例**：告诉 AI 什么不能做
- 关键规则必须有**原因**：避免未来重复犯同样错误

## 三、压缩信息熵的策略

### 3.1 为什么需要压缩

AI 上下文窗口有限。长对话会**压缩历史**，导致：
- 早期约定被遗忘
- 用户偏好丢失
- 项目约束模糊

**解决方案**：把易遗忘的内容**外置到文件**。

### 3.2 哪些内容必须外置

| 内容类型 | 是否外置 | 外置位置 |
|---------|---------|---------|
| 项目架构说明 | ✅ 必须 | `project_rules.md` |
| 命名规范 | ✅ 必须 | `project_rules.md` |
| 禁止事项清单 | ✅ 必须 | `project_rules.md` |
| 个人偏好 | ✅ 必须 | `user_profile.md` |
| 一次性操作步骤 | ❌ 不必 | 对话中说明即可 |
| 临时调试命令 | ❌ 不必 | 对话中说明即可 |

### 3.3 检查清单原则

**每次完成修改后，在回答末尾附上检查清单**。这能：
- 强制 AI 反思是否遗漏
- 给用户明确的验收标准
- 沉淀"完成一件事需要关注哪些维度"

## 四、跨对话记忆传递

### 4.1 新对话的标准开场

AI 在新对话中**必须主动读取**项目规则文件，而不是等待用户提醒：

```
1. 读取 user_profile.md（用户偏好）
2. 读取 .trae/rules/project_rules.md（项目约束）
3. 读取 .trae/rules/meta_rules.md（本文件）
4. 简单复述关键约束，证明已加载
5. 等待用户指令
```

### 4.2 经验积累的循环

```
用户提出任务
    ↓
AI 执行
    ↓
遇到错误/获得反馈
    ↓
AI 主动提议："这个经验值得加到规则中吗？"
    ↓
用户确认 → AI 更新规则文件
    ↓
下次新对话自动加载该经验
    ↓
（循环）
```

### 4.3 避免"猴子掰玉米"

- ✅ **持续积累**：每次新经验都叠加，不删除旧经验
- ❌ **不要重置**：不要因为项目重构就清空所有规则
- ✅ **标注版本**：规则条目附带"v2.0 引入"等时间标记
- ✅ **定期整理**：每 5-10 个版本做一次"规则瘦身"，合并相似条目

## 五、AI 行为准则

### 5.1 沟通风格

- **语言**：跟随用户最新一条消息的语言
- **简洁度**：能用一句话说清的不用三句
- **避免**：客套话、重复确认、过度解释
- **必须**：变更说明与实际编辑点一一对应

### 5.2 工具使用

- **修改前必读**：用 `Read` 读取文件后再用 `Edit`/`Write` 修改
- **批量并行**：独立的工具调用必须并行
- **避免大爆炸**：修改前先列出修改计划
- **本地沙箱限制**：某些工具（如 `hexo generate`）沙箱内不可用，需说明

### 5.3 错误处理

- **不掩盖错误**：工具调用失败要明确说明
- **不暴力重试**：失败后考虑替代方案或询问用户
- **不假设成功**：执行完命令后必须验证结果

### 5.4 隐私与安全

- **Token 不入仓库**：永远不要把 GitHub Token、API Key 写入文件
- **撤销泄露的 Token**：发现 token 泄露立即提醒用户撤销
- **隐私检查**：每次推送前扫一遍敏感信息

## 六、规则维护工作流

### 6.1 新增规则的标准流程

```
1. AI 在对话中识别可沉淀的经验
2. AI 提议："建议将 [xxx] 添加到 [规则文件] 的 [章节]"
3. 用户确认
4. AI 执行修改
5. AI 回答末尾附上检查清单
6. AI 提交并推送
```

### 6.2 规则条目的生命周期

```
提出 → 试行 → 确认 → 长期保留
              ↓
            淘汰（如过时、与新规则冲突）
```

### 6.3 规则冲突解决

当新规则与旧规则冲突时：
1. **新规则优先**（除非用户明确要求保留旧规则）
2. 在旧规则旁标注"已废弃，见 xxx"
3. 不直接删除，保持版本可追溯

## 七、Git 与历史管理

### 7.1 Git 历史包含敏感信息

**GitHub 历史会保留所有提交**，即使文件被删除。常见风险：
- Token 泄露
- 隐私数据（综述、数据、图表）
- 内部信息

**清理方案**：
1. 使用 `git filter-branch` 或 `git-filter-repo` 重写历史
2. 删除远程仓库并重建
3. 撤销并重新生成 Token

### 7.2 重写历史的命令

```bash
# 删除特定文件的历史
git filter-branch --force --index-filter \
  "git rm --cached --ignore-unmatch 'path/to/file'" \
  --prune-empty --tag-name-filter cat -- --all

# 或使用 git-filter-repo（推荐）
git filter-repo --path "path/to/file" --invert-paths
```

### 7.3 重写后必须做

- `git reflog expire --expire=now --all`
- `git gc --prune=now --aggressive`
- 强制推送到远程：`git push --force --all`
- **撤销所有可能泄露的 Token**

## 八、Trae 平台特定规则

### 8.1 规则文件必须以 UTF-8 无 BOM 编码

PowerShell `Set-Content` 默认带 BOM，**禁止使用**。必须用：
- Trae IDE 的 `Write` 工具
- `Out-File -Encoding utf8`（注意是 `utf8` 不是 `utf-8`）
- VSCode 等编辑器

### 8.2 规则文件位置

```
项目根目录/.trae/rules/
├── project_rules.md    # 项目特定规则
└── meta_rules.md       # 本文件（通用元规则）
```

### 8.3 规则更新的提交

每次更新规则文件后：
1. 提交：`git commit -m "v{版本}：{更新说明}"`
2. 推送：`git push`
3. 推送前扫描 token 等敏感信息

## 九、常见误区

### 9.1 ❌ "我以为你会记得"

AI 不会跨对话记忆。所有重要约定必须写入文件。

### 9.2 ❌ "这是特殊情况，不用写规则"

特殊情况往往是高频重复情况。写下来，下次就省事。

### 9.3 ❌ "规则太多了，会干扰 AI"

规则越精炼越好。**质量 > 数量**。每条规则必须经过验证。

### 9.4 ❌ "一次对话完成所有事"

复杂任务应**分多轮**：
1. 第一轮：理解需求
2. 第二轮：制定方案
3. 第三轮：执行
4. 第四轮：验证

每轮结束更新一次规则。

## 十、自我进化原则

> **这份元规则本身也要持续更新**。

如果发现：
- 某个章节从未被使用 → 考虑删除
- 某个原则频繁违反 → 加强说明
- 某个新场景没有规则 → 补充章节

**用户和 AI 是共同维护这份规则的协作者**。
